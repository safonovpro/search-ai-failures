# Ищем «НЕ успехи» ИИ в публичном Интернете

Основная задача проекта поиск в публичном интернете статей/постов на тему «НЕ успехи» искуственного интелекта (ИИ)».
Не интересуют конректные ошибки ИИ в моменте, а скорей интересует связка «внедрение ИИ → негативные последствия».
Интересует как частный опыт людей внедривших ИИ в свою личную и профессиональную деятельность, так и корпоративный опыт.

Примеры хороших публикаций:

1. Компания `X` внедрила ИИ и решила уволить `N`% сотрудников, решив, что они ей больше не нужны, а через время `T` стала нанимать обратно, т.к. проявилис `негативные последствия`
2. Человек `X` доверил ИИ часть/полностью свою личную/рабочую переписку, это привело к `негативным последствиям`
3. Внедрение ИИ компанией/человеком `X` в рабочий процесс, привело к тому, что черещ время `T` `X` потерял бдительность, очередной раз доверившись ИИ, что привело к `негативным последствиям`

**Ценность публикации поднимается особо**, если в ней по мимо фиксации проблемы, есть аналитика и выводы как можно/нужно избегать аналогичных проблем.

Примеры плохих публикаций:

1. Меня (человека `X`) уволили из-за ИИ
2. ИИ тормозит, а не ускоряет мою (человек `X`) работу
3. Внедрение/развитие ИИ компанией `X` является ошибкой (т.е. частное мнение, не подкреплённое фактами и реальным, доказанным негативным опытом)

## Как это работает

### Забор исходных данных

Агент последовательно обходит источники с текущими настройками запросов (запрос, временная глубина и др. фильтрующие параметры), 
результаты запросов сохраняются в базу данных и файлы в папку  `search_result/YYYY-MM-DD-HH-MM-SS/[source-domain].md`, 
где `YYYY-MM-DD-HH-MM-SS` это время запуска, а `source-domain` доменное имя источника (например `habr.com`, `reddit.com` и т.д.). 
Результирующие md-файлы формируются по следующему шаблону:

```md
# source-domain

**Дата и время запуска**: HH-MM-SS YYYY-MM-DD
**Количество публикаций в файле**: 000
**Параметры запроса**: [перечислены параметры запроса]

## Найденные публикации

### Название публикации № 1 | опубликовано HH-MM-SS

URL: [url-публикации-1]

Карткое описание публикации № 1 (как в источнике или суммаризация силами агента, до 1-2 абзатцев текста)

### Название публикации № 2 | опубликовано HH-MM-SS

URL: [url-публикации-2]

Карткое описание публикации № 2 (как в источнике или суммаризация силами агента, до 1-2 абзатцев текста)
```

Дополнительно агент сохраняет данные о публикации в базу данных в таблицу sources:

```md
| id | domain     | title | url   | published_at | searched_at         |
|----|------------|---------------|--------------|---------------------|
| 1  | habr.com   | ...   | ...   | HH-MM-SS     | YYYY-MM-DD-HH-MM-SS |
| 2  | reddit.com | ...   | ...   | HH-MM-SS     | YYYY-MM-DD-HH-MM-SS |
```


### Формирование отчёта

Далее агент идёт по сохранённым файлам из предыдущего шага и формирует отчёт в формате markdown. Сверяясь с
талицей в БД sources и url, исключая статьи, которые уже когда-то анализировались. Шаблон отчёта следующий:

```md
# Отчёт от DD-MM-YYYY HH-MM-SS

| Источник   | Заголовок                                   | Дата публикации     | Релевантность (от 1 до 10) |
|------------|---------------------------------------------|---------------------|----------------------------|
| habr.com   | [Название публикации № 1](url-публикации-1) | HH-MM-SS YYYY-MM-DD | 10                         |
| reddit.com | [Название публикации № 2](url-публикации-2) | HH-MM-SS YYYY-MM-DD | 9                          |

N - статей не включено в отчёт из-за 0 (нулевой) релевантности.

```

* Релевантность - это оценка LLM на сколько статья соответсвует исходной задаче (10 - очень релевантная, 1 - не релевантная)
* При необходимости (крайний случай) LLM должна сходит на страницу публикации и прочитать её полность для более точной оценки
* Все публикации сортируются по убыванию релевантности (от 10 до 1)
* Публикации с 0 релевантностью не входят в отчёт
* Полностью пустой отчёт нормальный результат, **не надо накпучивать релевантность**, чтобы заполнить таблицу хоть чем-то

## Стек технологий

1. [Koda Desktop](https://docs.kodacode.ru/desktop/index.html) — в качестве LLM-инструмента выполняющего [регулярные задачи](https://docs.kodacode.ru/desktop/features/scheduler.html).
2. MCP-сервера для изучаемых источников
3. Python (кастомные парсеры и скрипты), Node.js (MCP-серверы)
5. SQLite для ведение ведение уже изученных источников и публикаций

### Файловая структура проекта

```
.
├── .kodacli            - настройки Koda
│   └── settings.json
├── .sandbox            - папка временных файлов и папок (песочница)
├── python              - кастомные python-скрипты
├── reports             - папка с отчётами
├── search_result       - папка с исходными данными из источников
├── LICENSE             - файл лицензии
└── README.md           - данный файл
```

## Источники информации

### Российские

1. [Хабр](https://habr.com/) - используется [habr-mcp](https://github.com/vvzvlad/habr-mcp)
2. [vc.ru](https://vc.ru/) - используется кастомный python-скрипт (см. папку `python/vc`)
3. [Пикабу](https://pikabu.ru/) - используется кастомный python-скрипт (см. папку `python/pikabu`)

### Международные

1. [reddit](https://www.reddit.com/) — используется [reddit-mcp-buddy](https://github.com/karanb192/reddit-mcp-buddy)
2. [GDELT](https://gdeltproject.org/) — используется [gdelt-mcp-server](https://github.com/cyanheads/gdelt-mcp-server)
3. [NewsData.io](https://newsdata.io/) — используется [newsdata-mcp](https://github.com/newsdataapi/newsdata.io-mcp) (даёт возможность, в т.ч. фильтровать по тональности за последние 48 часов)
